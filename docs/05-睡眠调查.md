# 睡眠调查报告（结论：本机不可用）

> 这份报告记录了 2026-11-16 ~ 11-17 的完整排查过程，包含 9 组对照实验。
> 结论对**同机型用户**有参考价值，对**上游开发者**是可复现的 bug 报告。

## 1. 一句话结论

**系统睡眠（S3）在本机不可用**：睡眠进入与退出在硬件层都成功，
但**唤醒后显示无法恢复**，最终触发 WindowServer 看门狗 panic。
这不是配置问题、不是补丁移植问题、也不是驱动版本问题（作者原版组合同样失败）。

**显示器睡眠（屏幕自动熄灭）可用**，且可优化为「只关背光」。

## 2. 硬件事实

### 2.1 固件声明了真实 S3

```asl
Name (_S0, Package (0x04) { 0x00, ... })
Name (_S3, Package (0x04) { 0x05, ... })   // Intel PCH：5 = S3
Name (_S4, Package (0x04) { 0x06, ... })
Name (_S5, Package (0x04) { 0x07, ... })   // 7 = 软关机
```

### 2.2 Windows 的视角（`powercfg /a`）

```
此系统上有以下睡眠状态:
    待机 (S0 低电量待机) 连接的网络      ← Modern Standby
    休眠
此系统上没有以下睡眠状态:
    待机 (S3)  当支持 S0 低电量待机时，禁用此待机状态
```

即：固件声明了 S3，但 Windows 依据 S0ix 能力禁用它；macOS 在 PC 上只会走 S3。

## 3. 现象

```
14:49:47  pmset: Entering Sleep state due to 'Software Sleep'
14:51:37  pmset: Wake from Normal Sleep [CDNVA] : due to RTC ...
          → 屏幕不再亮起（用灯照可见内容，说明面板仍在显示，仅背光关闭）
          → 约 120 秒后：userspace watchdog timeout (WindowServer) → panic
```

## 4. 两种 panic

### 4.1 GPU 强制唤醒超时（开启加速）

```
panic: "[IGPU] ERROR: SafeForceWake acknowledgement never received on RENDER domain,
fFlags.systemInSleep: 0, fFlags.enabled: 1" @tgl/IntelAccelerator.cpp:8402

IntelAccelerator::SafeForceWakeMultithreaded(bool,unsigned,unsigned) + 0x45f
IntelAccelerator::SafeForceWake(bool,unsigned) + 0x18b
org.b00t0x.WhateverXe: xelpRegularForceWakeProtected(void*,bool,unsigned) + 0x9d
org.b00t0x.WhateverXe: XE::wrapTGLHostSubmit(void*,unsigned) + 0x19e2
IGHardwareCommandStreamer5::prepareExecListAndSubmit(...) + 0x9b
...
handleSoftwareContextSwitchInterrupt
```

含义：GPU 电源域正在关闭时，中断上下文仍有命令提交，提交前的强制唤醒得不到硬件应答。

### 4.2 WindowServer 看门狗（唤醒后）

```
panic: userspace watchdog timeout: no successful checkins from WindowServer
(1 induced crashes) in 120 seconds
```

含义：唤醒后 WindowServer 拿不到可用的显示（`Display ... not ready`），120 秒后看门狗 panic。

## 5. 九组实验

| # | 方案 | 结果 | 说明 |
|---|---|---|---|
| 1 | 原生 S3 | 关机 | `SMC shutdown cause: 5` |
| 2 | `_S3` 5→7 | 卡死 | SLP_TYP 7 行为异常 |
| 3 | GPRW + XPRW | 无变化 | 睡眠未发生，防秒醒无意义 |
| 4 | S0ix（DEEPIDLE + S0ixStandby） | 无变化 | `deep_idle_count=0`，macOS 不选 Deep Idle |
| 5 | 移除电池 SSDT | 同样 panic | 排除电池轮询 |
| 6 | 全套 pmset + 退出重负载应用 | 同样 panic | 排除电源策略 |
| 7 | `-wex-noaccel` | **能睡能醒**（108 s） | 证明加速器是阻塞点；但无加速、背光不恢复 |
| 8 | `-wex-tgl-hold-render-wake` | WindowServer 挂死 | 按住 render wake 破坏电源管理 |
| 9 | 作者原版组合 | 失败 | 排除配置/移植/版本因素 |

## 6. 采样器证据

用 launchd 守护进程每秒记录，判断「系统是否真的挂起」：

```
跳变 14:55:20 → 14:55:31 (11s)      ← 卡顿
跳变 13:40:37 → 13:41:06 (29s)      ← 真实挂起（noaccel 测试）
```

- 有加速时：只有 5–11 秒卡顿，**从未真正挂起**（提交竞争 → panic）
- 无加速时：出现 29–108 秒空白，配合 `Wake from Normal Sleep`，**证明 S3 真在工作**

## 7. 代码层面的三个发现

1. **softsleep 开背光逻辑永远失败**（`pp & 1` 条件 + 无条件清标志），已修（见 docs/03 §4）
2. **0.8.1 的唤醒通知修复只覆盖 DSI 路径**，eDP 路径的 `Display not ready` 仍然存在
3. **睡眠过渡期间的提交竞争**：`wrapTGLHostSubmit` 在睡眠窗口内未做拦截

## 8. 给上游的建议

1. 在睡眠窗口内丢弃或延迟 `wrapTGLHostSubmit` 的提交
2. `force-wake` 在 GPU 已断电时应快速失败，而不是等待永远不会来的 ACK
3. 把 0.8.1 的唤醒通知修复扩展到 eDP 路径
4. 修正 softsleep 的背光使能逻辑

## 9. 用户侧结论

```bash
sudo pmset -a disablesleep 1 sleep 0 hibernatemode 0 standby 0 powernap 0 tcpkeepalive 0
```

- 不要点「睡眠」，不要合盖
- 长时间离开请**直接关机**
- 显示器睡眠可正常使用
