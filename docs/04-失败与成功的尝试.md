# 从尝试 → 失败 → 成功：一份简要实验报告

> 这份报告记录我们踩过的坑，供同机型或其他机型用户参考。
> 每个条目都写明「目标 → 试了什么 → 结果 → 最终方案」。

## A. 电池：从「有电量没充电」到「完整状态」

| 阶段 | 做法 | 结果 |
|---|---|---|
| 初始 | 只有 DSDT 电池，`ACPIBatteryManager`（RehabMan） | ✅ 有电量百分比；❌ 无充电状态、无闪电图标 |
| 尝试 1 | 换 `SMCBatteryManager` | ❌ 完全不显示（日志：`failed to find batteries or adapters!`） |
| 尝试 2 | 读源码定位原因 | 需要 **同时**存在 `PNP0C0A` 电池与 `ACPI0003` 适配器 |
| **成功** | 新增 `SSDT-ADPX` 发布 `ACPI0003`，`_PSR` 读 EC 的 `ACIN` | ✅ 电量、充放电、闪电图标全部正常，插拔即时刷新 |

**教训**：SMCBatteryManager 在缺适配器时是**整体放弃**，不是降级运行。

## B. Fn 亮度键：从「键盘全废」到「EC 层转发」

| 阶段 | 做法 | 结果 |
|---|---|---|
| 初始 | 直接按键 | ❌ 无反应（按键不经过 PS2/HID，是 EC 触发的 ACPI 查询） |
| 尝试 1 | 改 VoodooPS2Keyboard 的 `Custom ADB Map`（加 `e02e=91`、`e020=90`） | ❌ **整个键盘失效**（键码映射写错） |
| 恢复 | 换回干净的 VoodooPS2 2.3.8 | ✅ 键盘恢复 |
| 尝试 2 | 找 EC 查询：DSDT 里 `_Q15`/`_Q16` | 确认亮度键走 EC |
| **成功** | 重命名 `_Q15`/`_Q16` → `XQ15`/`XQ16`，新增 `SSDT-BRTN` 接管并 `Notify(GFX0.DD02, 0x86/0x87)`，配 `BrightnessKeys.kext` | ⚠️ 部分可用（EC 时序问题偶发无响应） |

**教训**：不要盲改 PS2 键码表；先确认按键到底走哪条路径。

## C. 亮度下限：五轮迭代

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 直接把输出 clamp 到 6.25% 下限 | ❌ 滑块 0–34% 全是同一个亮度（死区） |
| v2 | 把苹果值按比例重映射到 `[lower, hw]` | ⚠️ 死区消失，但底部出现「反向变亮」 |
| v3 | 顶部饱和处理 | ❌ 无效果（问题不在顶部） |
| v4 | 恒等映射 + 4% 下限 | ❌ 底部 4 档合并成一档 |
| **v5（采用）** | `floor = hw/16`，`scaled = floor + value*(hw-floor)/donor` | ✅ 无死区、无合并、最低 6.25% 不黑屏 |

**教训**：改背光前先确认**改的是哪条路径**——我们一开始改的是 DSI 的
`kern_dsi_backlight.hpp`（本机根本不用），白改一轮。

## D. 显示器睡眠：从黑屏到可用

| 阶段 | 做法 | 结果 |
|---|---|---|
| 0.8.0 原生 | 无补丁 | ❌ 开机黑屏：`Phase 2 of link training failed`、`FB0 is not enabled` |
| 尝试 1 | 补丁 02（keep）：沿用固件链路 | ✅ 能开机；❌ 关屏后再也点不亮 |
| 尝试 2 | 补丁 04：屏蔽 DPCD `0x00E` bit7（130 ms → 0.6 ms 轮询） | ✅ 关屏/唤醒正常 |
| **增强** | `-wex-tgl-edp-softsleep`：只关背光保留链路 | ✅ 唤醒从「完整重训」变成 `Partial modeset by updating scaler` |

**教训**：`0x00E` 的 bit7 是「扩展能力标志」，不是等待时间——把整字节当等待时间会等 130 ms，
屏早就失锁了。

## E. 系统睡眠：八种方案全部失败（结论：本机不可用）

| # | 方案 | 结果 |
|---|---|---|
| 1 | 原生 `_S3`（SLP_TYP 5 = 真实 S3） | 「睡眠」变关机 |
| 2 | `_S3` 5→7 补丁 | 黑屏 + 风扇转 + 卡死 |
| 3 | SSDT-GPRW + GPRW→XPRW（防秒醒） | 无变化 |
| 4 | S0ix：`SSDT-DEEPIDLE` + `S0ixStandby 0.5.4` | `IOPMDeepIdleSupported=Yes` 但 `deep_idle_count=0`，macOS 不采用 |
| 5 | 移除电池 SSDT + `ACPIBatteryManager` | 同样 panic（排除电池） |
| 6 | 全套 `pmset` + `Hibernatemode=None` + 退出重负载应用 | 同样 panic |
| 7 | `-wex-noaccel`（关加速） | ✅ **能睡能醒**（108 秒），但唤醒后背光不恢复 |
| 8 | `-wex-tgl-hold-render-wake` | 无 force-wake panic，但 WindowServer 挂死 → 看门狗 panic |
| 9 | **作者原版组合**（其 config + 6 SSDT + 预编译 0.8.0 + Compat 0.8.0） | ❌ 仍然失败 |

**结论**：睡眠进入/退出在硬件层成立，**唤醒后显示恢复失败**，属驱动层缺陷。
详见 [docs/05-睡眠调查.md](05-睡眠调查.md)。

## F. 音频：一次「静音」事故

| 阶段 | 做法 | 结果 |
|---|---|---|
| 追求安静启动 | 去掉 `-v` 与 `debug=0x100` | ✅ 启动安静 |
| 同时误删 | 连 `keepsyms=1` 一起删了 | ❌ 音频栈静默失效（SimpleHDA 依赖它） |
| **修复** | 只删 `-v`/`debug=0x100`，保留 `keepsyms=1` | ✅ 安静 + 有声 |

**教训**：`SimpleHDA` 依赖 `keepsyms=1`，删 boot-args 要逐个确认。

## G. 稳定性：GPU 复位与强制断电的连锁反应

| 现象 | 原因 | 处理 |
|---|---|---|
| WindowServer 被杀（`Display ... not ready`） | GPU 复位 | 重启 |
| panic 后触摸板失效 | I2C 控制器状态卡住 | **完全关机**（不是重启）再开机 |
| ESP（FAT32）挂载失败 | 强制断电导致文件系统脏 | `fsck_msdos -fy /dev/rdiskN s1` |
| 亮度/声音偶发异常 | GPU 复位后状态未恢复 | 重启 |

## H. Fn+F6/F7/F8 热键：从「完全找不到」到实现

| 阶段 | 尝试 | 结果 |
|---|---|---|
| 1 | HID 抓取（过滤版 `hidsniff2`） | ❌ 无任何事件 |
| 2 | HID 抓取（全量 `hidsniff`，含厂商页 0xFF00） | ❌ 仍无事件 |
| 3 | Windows 下直读 EC RAM `0xFE0B0300`（256 字节，含按住 10 秒） | ❌ 无变化 → 热键不写 EC RAM |
| 4 | 在 DSDT 里找 `_Qxx` | ❌ 只有电池/盖子/热区 10 个查询 |
| 5 | 取证官方 OSD 软件（`OSDServiceDaemon.sys` / `OSDService.exe`） | 🔍 内核驱动只写注册表；用户态走 **WMI** |
| 6 | 导出全部 35 张 ACPI 表，逐张分析 | ✅ **SSDT 第 21 张**里有 `WMID` + `_Q2B/_Q66/_Q08` → `QV20(1/2/3)` |
| 7 | 编码测试 v1：三个查询全发 `0x87` | ❌ 三个键都变暗 → 无法区分（**方向搞反**） |
| 8 | 编码测试 v2：`_Q2B→0x86`、`_Q66→0x87`、`_Q08→0x86` | ✅ F6 变亮、F7 变暗、F8 变亮 → **映射确认** |
| 9 | 想用 ACPI Debug 直接 dump EC 内存 | ❌ 加 `acpi_layer/level=0xFFFFFFFF` 后开机卡死（日志洪峰）→ 放弃 |
| 10 | SSDT 建 `HKEY` 设备 + 写 `MIFSKeys.kext` | ⚠️ kext 加载了但匹配不到（缺 `registerService()`） |
| 11 | 修正 `IONameMatch`（用 `_HID` 值 `MIFS0001`）+ 补 `KMOD_EXPLICIT_DECL` | ✅ 匹配成功 |
| 12 | 写 `mifskeysd` 守护进程 | ✅ F6/F7/F8 全部可用 |

### 关键认知

1. **热键的 EC 查询定义在厂商 SSDT，不在 DSDT** —— 这是"找不到"的根本原因
2. **macOS 会派发 SSDT 里的 `_Qxx`** —— 所以"改名 + 自建 SSDT 重定义"可以拦截
3. **ACPI 通知码方向**：`0x86` = 增强亮度、`0x87` = 降低（测试设计必须用方向区分，否则无效）
4. **动作在用户态**：截图/任务视图/显示器设置没有内核 API → 必须有一个小守护进程

详见 [Packages/MIFS/README.md](../Packages/MIFS/README.md) 与 [docs/10](10-Fn热键实现计划.md)。

## I. 开机亮度自动跳高：从「以为驱动坏了」到「NVRAM 残留」

| 阶段 | 做法 | 结果 |
|---|---|---|
| 1 | 目测：关机前调低 → 开机后自动变亮（最多两次，目标约 0.88） | 🔍 现象确认 |
| 2 | 猜 ALS（环境光）自动亮度 | ❌ 无 ALS 驱动、无环境光节点 |
| 3 | 猜 macOS 恢复默认值 | ❌ BezelServices 里没有亮度键 |
| 4 | **写亮度记录器**（LaunchDaemon，每 200ms 采样 `/var/log/brightness.log`） | ✅ 抓到精确时间线 |
| 5 | 日志显示：`uptime 54s → 0.75`，`uptime 90s → 0.8799`（跳变） | 🔍 跳变目标 ≈ 0.88 |
| 6 | 检查 NVRAM：`backlight-level`（Apple）会随调整更新；`nmintelfb-brightness` **恒为 88** | ✅ 找到嫌疑 |
| 7 | `sudo nvram -d nmintelfb-brightness` + 重设一次亮度 | ✅ |
| 8 | 连续两次重启验证：0.20 → 0.20、0.625 → 0.625，**无跳变** | ✅ 修复确认 |

### 原理（为什么会这样）

```
旧驱动（nmx/IrisXe）在 NVRAM 写下 nmintelfb-brightness = 88 (0.88)
        ↓ （驱动卸载了，变量还在）
每次开机：AppleBacklight 先恢复 backlight-level（正确值）
        ↓
某个恢复路径又读到 88 → 把亮度设成 0.88 → 看起来"自动变亮"
```

关键点：**NVRAM 是断电不丢的**，删驱动不会删变量，所以问题会一直存在。

### 这次改了什么（用户常问）

| 层面 | 是否修改 |
|---|---|
| EFI / OpenCore 配置 | ❌ |
| macOS 系统文件 | ❌ |
| 已安装的驱动 kext | ❌ |
| **NVRAM 变量** | ✅ 删了一个残留值 |

### NVRAM 是什么（与 BIOS / EC 的关系）

| 项目 | 说明 |
|---|---|
| NVRAM | 主板上的非易失存储，UEFI 用来存启动项、boot-args、部分设备状态 |
| 与 BIOS | 属于固件环境；BIOS 设置界面改的就是它 |
| 与 EC | 两回事。EC 有自己的 RAM 窗口（`0xFE0B0300`），NVRAM 由芯片组/UEFI 管理 |
| 访问 | macOS `nvram` 命令；Linux `efivars`；Windows「UEFI 变量」 |

### 重启 vs 完全关机

NVRAM 非易失 → **两种启动方式读到的值相同**，因此：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 重启 | ❌ 跳到 0.88 | ✅ 正常 |
| 完全关机再开机 | ❌ 同样跳 | ✅ 正常 |

## J. 发布包：中文文件名乱码与上传失败

| 阶段 | 做法 | 结果 |
|---|---|---|
| 1 | 用 `git archive` 生成 release zip | ⚠️ zip 无 UTF-8 标志位 |
| 2 | 用 `unzip` 解压验证 | ❌ **中文名文件被静默跳过**（`docs/` 整个目录缺失） |
| 3 | 用 `ditto -x -k` 解压 | ✅ 正常（说明是工具差异，不是包坏了） |
| 4 | 改用 `tar 导出 + zip` 打包 | ✅ `unzip` 也能正常解压 |
| 5 | 引入 7-Zip（`7zz a -tzip -mcu=on`） | ✅ UTF-8 标志，全工具兼容 |
| 6 | 把 `7zz` 与打包脚本内置进仓库 | ✅ `Tools/bin/7zz` + `Tools/pack-release.sh` |
| 7 | GitHub API 上传附件 | ❌ `uploads.github.com` 无法连接（代理只代理了 api.github.com） |
| 8 | 换 Clash 规则代理 | ✅ 302，上传成功（160MB 约 11 分钟，245 KB/s） |

### 结论

- **不是所有解压都会乱码**，取决于工具：
  - Finder / `ditto` / 7-Zip / WinRAR / Keka：✅
  - 命令行 `unzip`（旧 zip）：❌ 跳过中文名文件
  - Windows 资源管理器自带：⚠️ 常乱码
- **v0.3.0 起统一用 7-Zip 打包**（`-tzip -mcu=on`）
- 旧版本（v0.1.0~v0.2.1）附件是旧 zip，已在 v0.3.0 的 Release 说明里加警示

## K. 追求 HiDPI 的三步走：命令无效 → BetterDisplay 强制 → 加速失效

| 阶段 | 做法 | 结果 |
|---|---|---|
| 1 | 当年用 **zep245 的 IrisXe 转译驱动**（z 开头，nmx）：**硬件加速可用**，但**没有 HiDPI**（3200×2000 只能 1:1，UI 极小） | ⚠️ 有加速、无 HiDPI |
| 2 | 执行 `sudo defaults write /Library/Preferences/com.apple.windowserver DisplayResolutionEnabled -bool YES` | 分辨率列表变成"老样式"的完整列表、出现更多档位，**但仍然没有 HiDPI 选项** |
| 3 | 下载 **BetterDisplay v5.2.1**（`~/Downloads/BetterDisplay-v5.2.1.dmg`），用它**强制设置分辨率/缩放** | ❌ **z 驱动硬件加速失效**（Metal 回退，UI 卡顿） |
| 4 | 换到 WhateverXe 0.8.x | ✅ **原生支持 HiDPI**（1600×1000 @ 90 Hz），无需任何工具 |
| 5 | 2026-11-18 恢复 `DisplayResolutionEnabled` 默认（删除该键） | ✅ 键已删除；HiDPI 仍正常（原生支持） |

### 关键纠正

- **`DisplayResolutionEnabled` 本身不破坏加速**：它只是让 WindowServer 把未声明支持的分辨率也列出来
- **真正导致加速失效的是 BetterDisplay 强制设置分辨率**：它把显示切到驱动未预期的模式
  （非原生像素格式/非常规帧缓冲尺寸），转译驱动的渲染路径因此回退或失效

### 教训

1. **优先用原生 HiDPI**：WhateverXe 0.8.x 已原生支持，不需要任何开关或第三方工具
2. **第三方强制改分辨率有风险**：可能切到驱动未适配的模式，代价是失去硬件加速
3. **`DisplayResolutionEnabled` 只是"显示更多选项"**，不等于"开启 HiDPI"
4. 若已改过，恢复默认：

```bash
# 查看
defaults read /Library/Preferences/com.apple.windowserver DisplayResolutionEnabled
# 恢复（删除该键）
sudo defaults delete /Library/Preferences/com.apple.windowserver DisplayResolutionEnabled
```

> 生效需注销/重启。本机 2026-11-18 已恢复，当前 3200×2000（UI 1600×1000 @ 90 Hz）正常。

## 一句话总结

> 能确定的是：**显示链路、亮度、电池、音频**都可以通过正确的补丁层解决；
> **系统睡眠**在这台机器 + 当前驱动下无解，问题在加速器的唤醒路径。
