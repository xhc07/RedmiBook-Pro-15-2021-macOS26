## 五、重要认识

1. **睡眠不是"不可用"，而是"能睡不能醒"** —— 这次证明 Deep Idle 能进能出（只是显示栈恢复失败）
2. **softsleep 是显示睡眠的必需品，但可能是系统睡眠的阻碍** —— 需要区分两条路径：
   - 显示睡眠（displaysleep）：需要 softsleep（partial modeset）
   - 系统睡眠（Deep Idle）：可能需要完整 retrain
3. **轮询进程必须全部停**才能进 Deep Idle（这点用户提醒得对）
4. **Fn 亮度键不依赖守护进程**（走 EC + BrightnessKeys 内核层），所以"还能调亮度"不代表守护进程没停

## 十、未来实验线索：上游 #192 的 DPLL/DKL PHY 恢复补丁（2026-11-23 记录）

### 来源

`b00t0x/WhateverXe` **#192**：「OLVED: TGL internal eDP stays black after S3 resume —
DKL PHY/DPLL left at reset values, fix included below」

- 机器：Lenovo AIO-16ITL，**i5-1155G7 / 9A49**，内屏 2560×1600 30-bit
- 系统：macOS 15.8.3，WEX 0.8.3 + Graphics 0.4.4
- 现象：S3 恢复后**内屏保持黑**，但硬件状态（`PP_CONTROL`、`DDI_BUF_CTL_A`、`PIPECONF_A`）与正常开机一致
- 根因：**DPLL / DKL PHY 分频器停在复位值**，帧率只有 17–22 fps（正常 60），驱动不再重新编程

### 为什么驱动不自己修

1. `invokeHotplugHandler` 走 closable-display 分支 → `Hotplug received on closable display - bailing out`
   → `enablePort` / `enableDklPhyClocks` / `enableClocks` 只在开机跑一次
2. resume 后缓存的时钟参数仍匹配（`paramsClockCompare` 成功）→ modeset 跳过 PLL 重编程

### 修复（3 处，全部是新增，不改现有逻辑）

```cpp
// 1) 用 setFramebufferPowerState 作为可靠的 resume 信号
uint32_t XE::wrapTGLFramebufferPowerState(void *fb, uint32_t state) {
    const auto r = FunctionCast(wrapTGLFramebufferPowerState,
                                callbackXE->orgTGLFramebufferPowerState)(fb, state);
    if (state != 2) tglResumeArmed = true;   // 2 = on
    return r;
}

// 2+3) hwSetMode：非 resume 时快照，resume 时写回
static const uint32_t tglPllRegs[5] = {0x164284, 0x164288, 0x164280, 0x162014, 0x162028};
static uint32_t tglPllGood[5];
static bool tglPllGoodValid, tglResumeArmed;

uint32_t XE::wrapTGLHwSetMode(void *controller, void *fb, const void *timing) {
    void *port = tglPortByDDIE ? tglPortByDDIE(0u) : nullptr;   // DDI A = 内屏 eDP
    if (port && tglPortRead && tglPortWrite) {
        if (tglResumeArmed) {
            tglResumeArmed = false;
            if (tglPllGoodValid)
                for (uint32_t i = 0; i < 5; i++)
                    tglPortWrite(port, tglPllRegs[i], tglPllGood[i]);
        } else {
            for (uint32_t i = 0; i < 5; i++)
                tglPllGood[i] = tglPortRead(port, tglPllRegs[i]);
            tglPllGoodValid = true;
        }
    }
    return FunctionCast(wrapTGLHwSetMode, callbackXE->orgTGLHwSetMode)(controller, fb, timing);
}
```

需要的符号：

```
__ZN31AppleIntelFramebufferController9hwSetModeEP21AppleIntelFramebufferPK29IODetailedTimingInformationV2
__ZN21AppleIntelFramebuffer24setFramebufferPowerStateEj
__ZN14AppleIntelPort12getPortByDDIEj
__ZN14AppleIntelPort14readRegister32Ej
__ZN14AppleIntelPort15writeRegister32Ej
```

### 注意事项（作者强调）

- 5 个值**运行时从驱动自己读取**，不硬编码 → 自动跟随分辨率/刷新率变化
- 所有寄存器读写必须走 `AppleIntelPort::readRegister32/writeRegister32`
  —— **裸 MMIO 读 `0x164xxx` 会挂住显示引擎**
- 每个符号都要校验偏移 + 指令字节签名，不匹配则跳过

### 对我们的适用性评估

| 我们的问题 | #192 能否解决 |
|---|---|
| 唤醒后内屏黑 / 冻结 | ⚠️ **可能部分有效**（DPLL 复位是候选原因之一） |
| 睡眠进入失败（softsleep 下） | ❌ 不能（它只处理 resume） |
| WindowServer 30 秒超时 / ME 12 秒延迟 | ❌ 不能（另一条链路） |

**结论**：属于"值得一试但不足以单独解决"的线索；且必须先做到"能睡"（去掉 softsleep）。
未来如果上游修好 WEX 唤醒路径，或我们重做 WEX 编译实验时，可优先移植。

## 十一、未来实验线索 2：上游 #87 的 DC9 断电思路（2026-11-23 记录）

### 来源

`b00t0x/WhateverXe` **#87**（DMC firmware / DC5-DC6 请求）在 2026-11-22 有两条新评论：

**@brandonedley（11-22）**：

> "在 **Alder Lake-P（8086:46A6）** 上用**真正的 DC9 断电**达到 **PC10 = 99%**（Deep Idle），
> **完全不需要把 Tiger Lake 的 DMC/CSR 固件上传到 Display 13**。
> For system sleep (Deep Idle), it turns out you **don't need DMC DC5/DC6 at all**
> if Display 13 actually powers its wells down cleanly for DC9."

**@macintelk（11-22）**：

> "the firmware list in linux is per platform. **better if u guys check how linux sets dc state on sleep
> and copy it**. also note linux has workarounds that wex/apple don't have"

### 对我们方向的含义

我们此前的主线是"**加载 Intel DMC 固件**"（两版实现：写 0 的错误版、修正 MMIO 表 + fixup 的正确版）。
两版都能修掉睡眠死锁，但：

- DMC 上传后待机功耗反而升高（@jkbuha 在 #87 的实测：4.37W → 9–11W，PC6 消失）
- 唤醒问题依旧（我们和 @Aqpcet 都是）

**#87 的最新结论说明**：对 "系统睡眠（Deep Idle）" 而言，**DMC 不是必需品**；
关键是让**显示电源井在睡眠时干净断电（DC9）**，由内核在进入 DC9 前完成电源井关闭。

### 若要继续，应该参考的 Linux 实现

| Linux 位置 | 作用 |
|---|---|
| `drivers/gpu/drm/i915/display/intel_display_power.c` | `intel_power_domains_suspend()` → 按 DC 状态关闭电源井 |
| `skl_pcode_request()` / `intel_display_power_put()` | 与 PCODE 协商 DC 状态 |
| `intel_dmc.c` → `intel_dmc_suspend()` | DMC 侧的 suspend（我们试过的部分） |
| `DC_STATE_EN` (0x45504) | 设置目标 DC 状态（DC5/DC6/DC9） |

### 与我们当前结论的关系

- 我们的睡眠问题**分成两半**：睡不进去 / 醒了不显示
- DMC 只能修"死锁"，不能修显示恢复
- **#192 的 DPLL 恢复补丁**修"唤醒后显示"
- **#87 的 DC9 断电思路**修"睡眠功耗与电源井状态"（可能让睡眠进入更干净）

**结论**：如果未来再试睡眠，正确的组合应该是：

```
DC9 断电（参考 Linux intel_display_power.c）
```
