### 技术要点（从 issue 讨论中整理）

| 步骤 | 寄存器 | 作用 | 备注 |
|---|---|---|---|
| 1 | `AUDIO_PIN_BUF_CTL` (0x48414) **bit 31** | 唤醒显示 codec | **必须在 AppleHDA 探测之前**（约 22-23 秒） |
| 2 | `HSW_AUD_CHICKENBIT` (0x65F10) **bit 15** | codec wake override（清 → 等 1ms → 置 → 等 1ms） | 同上，时序关键 |
| 3 | `AUD_FREQ_CNTRL` (0x65900) | **TGL 特有**：BIOS 值若为 `0x9010`（坏值）需改成 `0x8010` | Linux `i915_audio_component_get_power()` 行为 |
| 4 | `PWR_WELL_CTL2` (0x45404) | 电源井（PW1/PW2/PW_A-C） | ADL 上固件已置好，TGL 需确认 |
| 5 | `AUD_PIN_ELD_CP_VLD` (0x650C0) | ELD valid + 音频输出使能 | 目标：bit 31 置位 + ELD 有效 |
| 6 | `AUD_CONFIG_B` | HDMI 像素时钟域 | 目标值应为非 0 |

## 三、方案 B：DMC 固件（修系统睡眠）

### 来源

| 项目 | 内容 |
|---|---|
| 上游 issue | [#157](https://github.com/b00t0x/WhateverXe/issues/157)（**我们提的**） |
| 实现者 | @Aqpcet（MECHREVO Forza 6，i5-11300H + 9A49，同 CPU！） |
| 状态 | **成功修复内核死锁**：睡眠→唤醒完成，Metal 正常 |

### 原理

WEX 不加载真正的 **DMC（Display Microcontroller）固件**，Apple 内置的 `_CSR_PATCH_AX` 只有 12,868 字节，
而真正的 Intel 固件是 17,840 字节 —— 内置的"对大多数显示器不起作用"。

### 固件

| 项目 | 值 |
|---|---|
| 来源 | linux-firmware `i915/tgl_dmc_ver2_12.bin` |
| 大小 | 19,760 字节 |
| 结构 | CSS 头 128B + package 头 400B + 主 DMC 头（0x210，version 3）+ 主 payload（0x310，17,840B）+ pipe DMC 头（0x48C0，220 dword） |
| 关键字段 | `start_mmioaddr 0x80000`、`mmio_count 9`、`fw_version 1.2` |

### 实现（约 80 行 + 固件数组）

| 步骤 | 内容 |
|---|---|
| 1 | `tglDMCUploadTo()`：寄存器访问管理器在 `controller + 0xc40`，写 4,460 dword 到 `0x80000`，写 9 个 MMIO 清零，回读校验 |
| 2 | Hook `AppleIntelFramebufferController::hwInitializeCState`（TGL framebuffer 16.0.0 偏移 `0x43972`）：先调原函数（上传 Apple 的 12,868B），再上传我们的 |
| 3 | Hook `IntelAccelerator::systemDidWake`（AppleIntelTGLGraphics 偏移 `0x2897A`）：唤醒后重新上传（Deep Idle 会清掉） |

### 结果

| 阶段 | 结果 |
|---|---|
| 修复前 | 系统睡眠 → **内核死锁**，必须断电 |
| 修复后 | 睡眠 → DarkWake → Maintenance Sleep → 电源键唤醒，**Metal 正常** |
| 状态属性 | `WEXTGLDMCLoaded/CHooked/CVerify/CWakeHooked` = Yes |
| 遗留问题 | 唤醒后 **modeset 触发 GPU hang**（WindowServer 看门狗 panic），外接屏无信号 |

### 遗留问题的线索

```
modeset → displayState OFF → Intel GPU hang (context 46) → WindowServer 卡死 → 看门狗
```

@Aqpcet 判断：缺的是 **RENDER domain 的 forcewake / 上下文恢复路径**，不是显示固件。
（与我们之前的 `SafeForceWake acknowledgement never received on RENDER domain` 同源。）

### 其他有用信息

- @macintelk：`-disablegfxfirmware` 只阻止 **GuC** 固件加载，**不影响 DMC**
- 睡眠问题的完整讨论还有 issue **#63**（TGL-U 9A49 eDP 黑屏）、**#141**（TGL-H S0ix 不唤醒）、**#166**（GPU hang 恢复）

## 三·五、DMC 方案核对（2026-11-19 实测后审计）

### 我们已实现 vs Aqpcet 描述

| 步骤 | Aqpcet | 我们 | 状态 |
|---|---|---|---|
| 下载 `tgl_dmc_ver2_12.bin`（19,760 B） | ✅ | ✅（校验字节数完全一致） | 一致 |
| 解析主 payload（@0x310，4,460 dword） | ✅ | ✅ | 一致 |
| 9 个 MMIO 偏移写 0（@0x270 表） | ✅ | ✅（0x8F074…0x8F010） | 一致 |
| 回读 `0x80000` 校验 | ✅ | ✅（Verify=Yes） | 一致 |
| Hook `hwInitializeCState`（0x43972） | ✅ | ✅ | 一致 |
| Hook `IntelAccelerator::systemDidWake`（0x2897A） | ✅ | ✅ | 一致 |
| 寄存器管理器 `controller+0xc40` | ✅ | ✅ | 一致 |

### 可能的疏漏（按影响排序）

| # | 疏漏 | 说明 | 影响 |
|---|---|---|---|
| 1 | **Pipe DMC 未上传** | 固件里还有第二段：pipe DMC 头 @0x48C0 + 220 dword payload（880 字节）。i915 会同时加载两段 | 可能影响 pipe 级功能（PSR/显示），**不确定是否与 RENDER panic 相关** |
| 2 | **未显式 enable/disable DMC** | i915 加载前会先禁用 DMC、加载后重新使能；我们只是覆盖内存，依赖 Apple 原有的使能流程 | 我们验证的是"内存内容"，不是"DMC 已运行" |
| 3 | **唤醒后指针可能失效** | 我们用启动时缓存的 controller 指针；若唤醒后 controller 重建，指针会过期 | 可能导致唤醒重载失败（但属性显示 WakeHooked=Yes，说明钩子本身在） |
| 4 | **`-disablegfxfirmware` 仍在** | 该参数禁用 **GuC** 固件（@macintelk 指出不影响 DMC） | **高度可疑**：GuC 缺失可能影响唤醒后的上下文恢复/forcewake |
| 5 | **`-wex-tgl-edp-softsleep` 改变唤醒路径** | 我们的唤醒是"partial modeset"，Aqpcet 可能是完整 modeset | 唤醒路径不同，panic 触发点可能不同 |

### 与本机 panic 的关系判断

本机 panic 在 `wrapTGLHostSubmit → xelpRegularForceWakeProtected → SafeForceWake`，
即 **RENDER 域 forcewake 超时**。Aqpcet 在同一位置也卡住（他明确说"剩余问题在 accelerator 的
电源管理，不是显示固件"）。因此：

- **1、2、3 不是本机 panic 的原因**（否则不会与他同点失败）
- **4、5 值得单独验证**，因为它们改变了唤醒时的 GPU 电源/上下文路径

| DMC 收益 | "修好睡眠死锁" | 但 @jkbuha 实测：DMC 加载后**待机功耗反而升高**（4.37W → 9-11W，PC6 消失） |

### 更可行的新方案：S0ixStandby

**仓库**：`labrouss/S0ixStandby`（★19，v0.5.4，BSD-3）

- 专为 **ACPI S3 缺失/损坏**的笔记本设计：让 macOS 用 **Deep Idle（S0 sleep）** 代替 S3
- 首台测试机：HP EliteBook 840 G8（Tiger Lake）
- **已测试：i5-11300H / TGL-H35 / 内屏（与我们的 CPU 相同）**
- 关键结论：**WhateverXe 的加速在睡眠后存活**（TGL Iris Xe，唤醒后 Metal 正常），"S0ixStandby 在唤醒时先重置 GPU"

**安装要求**：

1. `SSDT-DEEPIDLE.aml` → `EFI/OC/ACPI/` + `ACPI > Add`
   （它提供 `\_SB.LPS0` 和 `\_GPE.LXEN`，只在 Darwin 下返回 1 → 让 macOS 认为支持 Deep Idle）
2. `S0ixStandby.kext`（Release）→ `EFI/OC/Kexts/` + `Kernel > Add`
3. `sudo pmset -a hibernatemode 0 standby 0 powernap 0 tcpkeepalive 0`
4. **Tiger Lake 需要 CPUID 伪装成 Ice Lake**：`Cpuid1Data = E5060700 00000000 00000000 00000000`
   （**我们已经是这个值** ✓）
5. 重启后检查：`ioreg -rd1 -c IOPMrootDomain | grep DeepIdle` → `IOPMDeepIdleSupported = Yes`

**已知限制**：

- 真实 SLP_S0 未置位（但包 C10 可达，功耗已在 Linux S0ix 范围）
- **AC 供电时**：dark wake 后重新入睡可能卡住（`GFX0(): Some drivers failed to handle setPowerState`），WEX 帧缓冲问题
