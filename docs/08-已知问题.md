# 已知问题与处理

## 1. 系统睡眠不可用（最重要）

**现象**：点「睡眠」后屏幕黑，系统看似停止响应；用灯照可见画面（仅背光灭）；
几十秒后自动重启；日志中有 `SafeForceWake` 或 WindowServer 看门狗 panic。

**原因**：驱动层缺陷（详见 [05-睡眠调查](05-睡眠调查.md)），非配置问题。

**处理**：

```bash
sudo pmset -a disablesleep 1 sleep 0 hibernatemode 0 standby 0 powernap 0 tcpkeepalive 0
```

- 不要点「睡眠」
- 不要合盖（合盖会保持运行且发热）
- 长时间离开请关机

## 2. 内置麦克风不可用

**现象**：系统里没有输入设备，或录音全是静音。

**原因**：本机麦克风是 Intel SST 的 DMIC 阵列，需要 DSP 固件与 macOS 的 SOF 栈；
macOS 没有对应驱动（HDA-legacy 与 DSP 在同一控制器上互斥）。

**处理**：用 USB 声卡 / USB 麦克风 / 蓝牙耳机。

## 3. Fn 亮度键偶发无响应

**现象**：按 Fn+F2/F3 有时有效，有时没反应。

**原因**：EC 查询（`_Q15`/`_Q16`）上报时序受 EC 固件控制，`BrightnessKeys` 依赖 ACPI 通知。

**处理**：用菜单栏亮度滑块作为替代；或按两次。

## 4. 电池循环次数显示 -1

**现象**：系统信息里「循环次数」为 -1。

**原因**：固件 `_BIX` 字段返回异常值（真实值可从 Windows 电池报告读到，本机为 3）。

**处理**：忽略；电量与充电状态不受影响。

## 5. panic 后触摸板失效

**现象**：一次 panic/强制断电后，触摸板完全无反应（`VoodooI2CHIDDevice` 实例为 0）。

**原因**：I2C 控制器状态未复位。

**处理**：**完全关机**（不是重启）→ 等 5 秒 → 开机。

## 6. ESP（EFI 分区）挂载失败

**现象**：`Volume on diskXs1 failed to mount`。

**原因**：强制断电导致 FAT32 脏。

**处理**：

```bash
sudo diskutil unmount force diskXs1
sudo fsck_msdos -fy /dev/rdiskXs1
sudo diskutil mount diskXs1
```

## 6.5 开机后亮度被自动调高（2026-11-18 已解决）

### 现象
- 关机前把亮度调低，开机后亮度会**自动跳高**（最多两次），跳到约 0.88
- 手动调回后仍会再跳

### 排查方法
写了一个开机自启的亮度记录器（每 200ms 采样，写 `/var/log/brightness.log`）：

工具在 [Tools/diagnostics/brightlogd](../../Tools/diagnostics/README.md)：

```bash
# 安装（一次性）
sudo cp Tools/diagnostics/brightlogd /usr/local/bin/
sudo cp Tools/diagnostics/local.brightlogd.plist /Library/LaunchDaemons/
sudo chown root:wheel /Library/LaunchDaemons/local.brightlogd.plist
sudo launchctl bootstrap system /Library/LaunchDaemons/local.brightlogd.plist

# 查看
cat /var/log/brightness.log
```

日志样例（跳变时）：

```
13:38:13  uptime= 54s  brightness=0.7500   ← 开机初始
13:38:47  uptime= 90s  brightness=0.8799   ← 自动跳高
```

### 根因
NVRAM 里残留了一个旧驱动（nmx / IrisXe）写入的变量：

```
nmintelfb-brightness = 88   （= 0.88，恒定不更新）
backlight-level      = 正常随亮度更新（Apple 的）
```

开机时这个残留值被恢复，覆盖了正确保存的亮度。

### 解决

```bash
sudo nvram -d nmintelfb-brightness
```

删除后重新设置一次亮度（让它以正确值保存），实测**连续两次重启**：

| 次数 | 开机亮度 | 跳变 |
|---|---|---|
| 第 1 次（0.20） | 0.2002 | 无 |
| 第 2 次（0.625） | 0.6250 | 无 |

### 说明

- **改的是 NVRAM（固件变量）**，不是 EFI、不是系统文件、不是驱动
- NVRAM 是非易失存储，**重启和完全关机都保留**，所以修复前后行为在两种启动方式下一致
- OpenCore 菜单里的 "Reset NVRAM" 也会清掉它（副作用是丢失启动项与 boot-args）

## 6.5.1 内置麦克风无声：与"USB 声卡为什么能独立工作"的区别（2026-11-19 查清方向）

**硬件情况**（实测）：

| 项目 | 值 |
|---|---|
| HDA codec | **Realtek ALC256**（`IOHDACodecVendorID = 0x10EC0256`） |
| layout | `alc-layout-id = 38`（我们的 `alcid=38`） |
| 平台 SoundWire | 有（`SNDW@40000000` + SWD0-5），但 DMIC 不在这条总线上 |
| SimpleHDA 的 DMIC 支持 | 只实现了 **CS4206 / CS4208（Cirrus）**，**不支持 ALC256** |

**关键区别：为什么 USB 声卡能"独立"，DMIC 不能**

| | USB 声卡 | 本机 DMIC |
|---|---|---|
| 数据形态 | 标准 USB Audio PCM 流 | **原始 PDM 比特流** |
| 时钟 | 设备自带 | 由 **codec 提供 CLK** |
| PDM→PCM 转换 | 设备内完成 | 由 **codec 内的抽取滤波器**完成 |
| 总线 | 独立 USB 总线 | 与扬声器共用 **HDA codec** |
| macOS 驱动 | 通用 `AppleUSBAudio` | 需要 codec 专用驱动 |

→ DMIC 不是独立设备，它和扬声器**共用同一个 ALC256 codec**。再挂一个驱动去抢同一个 codec 的寄存器/verb，就会和 HDA 驱动冲突（这就是"会冲突"的意思）。

**真正可行的修法**：

1. **扩展 AppleALC/SimpleHDA**，为 ALC256 实现 DMIC 使能 verb（引脚复用 + 时钟 + 抽取滤波配置）—— 需要 codec 手册级别的资料，中等工作量
2. 用 **USB 麦克风/耳麦**（独立设备，立刻可用）
3. 若 DMIC 在 SoundWire 上，还需要 Intel SoundWire 驱动（macOS 没有）

**2026-11-19 补充：确认走的是 Intel SST / SoundWire**

Windows 下这块麦克风阵列显示为 **「Intel 智音技术」（Intel Smart Sound Technology, SST）**，
说明它挂在 Intel 的音频 DSP 上，而不是 HDA codec。

本机实测证据：

| 证据 | 值 |
|---|---|
| ACPI 表 | 含 `SNDW`(4)、`SWD0`(2)、`SST`(36) |
| ioreg | `HDEF@1F,3 → SNDW@40000000 → SWD0…SWD5` |
| codec | ALC256（只负责模拟输出/输入） |

**结论**：麦克风在 **SoundWire 总线**上，由 Intel SST DSP 驱动。
macOS 没有 Intel SST / SoundWire 驱动 → **这条路径在 macOS 上不可实现**。

**与 AMD 版本的区别**：AMD 平台没有 Intel SST，厂商通常把 DMIC 接到 **ALC codec 的 DMIC 引脚**
（或 AMD ACP）。所以 AMD 版本的麦克风在 macOS 上反而更可能有戏——但**我们这台 Intel 机器的
麦克风物理上接在 SoundWire 上，无法通过软件改接到 codec**。

### AMD 版是怎么做到的（2026-11-19 分析源码）

下载了 [qhuyduong/AMDMicrophone](https://github.com/qhuyduong/AMDMicrophone) 源码（★61，约 500 行 C++）。

**它是把 Linux 的 AMD ACP WOV（Wake-on-Voice）PDM 驱动移植到 IOKit**，证据：

```
ACP_WOV_PDM_ENABLE                 0x1242C04
ACP_WOV_PDM_DMA_ENABLE             0x1242C08
ACP_WOV_RX_RINGBUFADDR/SIZE        0x1242C0C/10
ACP_WOV_PDM_NO_OF_CHANNELS         0x1242C28
ACP_WOV_PDM_DECIMATION_FACTOR      0x1242C2C
ACP_WOV_CLK_CTRL                   0x1242C60
```

启动流程（`startDMA`）：

```
清 FIFO → 开时钟 → ACP_WOV_PDM_ENABLE=1 → ACP_WOV_PDM_DMA_ENABLE=1
→ 轮询 DMA 状态 → 环形缓冲 + MSI 中断 → IOAudioEngine 输出 PCM
```

**关键：AMD 的 ACP 有独立的 PDM 硬件引擎**（自带抽取滤波 `DECIMATION_FACTOR` + DMA），
**不需要 DSP 固件**，所以 500 行寄存器操作就能出声。

### 为什么同样思路在 Intel 上不行

| | AMD ACP | Intel（我们） |
|---|---|---|
| 麦克风路径 | ACP 内 **独立 PDM 引擎** | Intel **SST DSP** + **SoundWire**（`SNDW`/`SWD0-5`） |
| PDM→PCM | **硬件抽取滤波**（寄存器配置即可） | 由 **DSP 固件**（SOF/AVS）处理 |
| 需要固件吗 | ❌ 不需要 | ✅ 需要 DSP 固件 + topology |
| Linux 驱动 | `snd_pci_acp3x` 直接寄存器操作 | `sound/soc/intel/avs` 或 SOF（加载 DSP 固件） |
| 移植难度 | 500 行寄存器 + DMA | 需要 SoundWire 控制器驱动 + DSP 固件加载 + topology |

**结论**：AMD 能移植是因为它的硬件有"傻瓜式"PDM 引擎；Intel 把这件事交给了 DSP，
而 macOS 既没有 Intel DSP 固件、也没有 SoundWire 栈。**这条思路无法照搬。**

**状态**：方向已查清，待实现（可选）。

## 6.6 `logd` 看门狗超时（开机早期，非致命，2026-11-18 记录）

**现象**：开机时偶发一个崩溃报告 / 弹窗，内容为：

```
logd: WATCHDOG, monitoring timed out for service
unresponsive dispatch queue(s): com.apple.firehose.drain-mem (tid:2006)
40 seconds since last successful checkin（uptime 约 70-80 秒）
displayState: OFF
```

**出现记录**：00:51、02:27、14:35（都是开机早期，uptime 70-80 秒）。

**判断**：**不是 panic，也不影响使用**。`logd` 是系统日志服务，它在开机早期
的日志洪峰中没有及时"签到"，看门狗判定超时并生成报告；系统随后自行恢复。

**可能原因**：

| 猜测 | 依据 |
|---|---|
| 开机日志洪峰 + 外置 USB SSD 写入慢 | 系统装在 USB SSD 上；`firehose.drain-mem` 是日志落盘队列 |
| WhateverXe 启动期日志量大 | 驱动初始化会打不少 IOLog |
| `keepsyms=1` 无法去掉 | SimpleHDA 依赖它，否则音频失效 |

**处理**：**忽略**。若想减少出现频率，可尝试：

- 减少开机日志：不加 `-v`（已做到）
- 换用更快的存储（内置盘不可写，暂不可行）

**状态**：良性，已记录，不做修复。

## 6.7 合盖后显示器不黑屏（2026-11-19 已解决 ✅）

**现象**：合上笔记本盖子后，**屏幕仍然亮着**（系统没有进入睡眠，显示器也没有关闭）。

**原因**（已确认的部分）：

```
pmset: SleepDisabled = 1              ← 我们主动禁用了系统睡眠（本机睡眠不可用）
ioreg: AppleClamshellCausesSleep = No  ← 系统因此不会因合盖而睡眠
```

本机系统睡眠在驱动层不可用（见 [docs/05](05-睡眠调查.md)），所以 `SleepDisabled=1` 是必须的。
但这也导致 macOS 不再走"合盖 → 关屏"的默认路径。

**修复思路（下次做）**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 用户态守护进程**（推荐） | 监听 `AppleClamshellState`，合盖 → `pmset displaysleepnow`；开盖 → `caffeinate -u -t 1` 唤醒 | 不动内核、可随时停 | 需要 1 个后台进程（可复用 MIFS 的模式） |
| B. ACPI 层 | SSDT 拦截 `_LID` / EC 盖子查询，合盖时 `Notify(DD02, ...)` 或直接关背光 | 零进程 | 需确认盖子事件走哪条路径；可能与电池/EC 补丁冲突 |
| C. 修改 `AppleClamshellCausesSleep` | 强制设为 Yes | 最直接 | 会导致系统尝试睡眠 → 触发已知的睡眠 panic，**不可行** |

**下次需要先做的验证**：

1. 合盖时 `ioreg -l | grep AppleClamshellState` 是否变成 `Yes`
2. 是否有 `AppleClamshellState` 的 IOKit 通知（还是必须轮询）
3. 合盖时 EC 是否发 `_Qxx`（可用 `fnprobe.sh` 观察）

**（2026-11-19 更新）对比 AMD 版本后的结论**

AMD 版（RedmiBook Pro 14 5700U / 15S 5600H）的 `SSDT-LID0` 做的是：

```asl
Method (_Q80) {
    LIDS = ECRD (RefOf (LSTE))
    Notify (LID0, 0x80)      // 通知盖子状态变化
}
```

**我们的 DSDT 已经做了同样的事，甚至更完整**：

```asl
Method (_Q80) {
    LIDS = ECRD (RefOf (LSTE))
    ^^^GFX0.GLID (LIDS)      // 把盖子状态告诉显卡驱动
    Notify (LID0, 0x80)
    Sleep (0x0A)
    If ((LIDS == Zero)) { Notify (^^^RP05.PXSX, 0xD5) }   // 合盖
    ElseIf ((LIDS == One)) { NTDG (...) }                 // 开盖
}
```

→ **ACPI 层（EC 查询 + 盖子通知 + GLID）本机是完整的**，不需要像 AMD 那样补 SSDT。

**真正的缺口在驱动侧**：`WhateverXe` 源码里没有 `GLID` / `CLID` / clamshell 相关处理，
所以显卡驱动不知道盖子关了 → 不会关背光。

**✅ 已解决（2026-11-19）**

实现了用户态守护进程 `Packages/MIFSLid`：

```
每 500ms 读 AppleClamshellState
   合盖 → pmset displaysleepnow
   开盖 → caffeinate -u -t 1
```

**实测**：

```
21:05:33  clamshell=Yes → mifslidd: lid closed -> displaysleepnow   → 屏幕熄灭
21:05:42  clamshell=No  → mifslidd: lid opened -> wake display      → 屏幕亮起
```

**踩坑**：最初读 `IOService:/IOResources/IOPMrootDomain` 路径错误（该服务不在 IOResources 下），
改用 `IOServiceMatching("IOPMrootDomain")` 后正常。

安装：`sudo bash Packages/MIFSLid/install.sh`

## 6.9 外接显示器热插拔后 WindowServer 卡死（2026-11-18 记录，待排查）

**现象**：连接外接显示器后**拔出**，系统卡死（画面冻结，约 40 秒后看门狗介入）。

**证据**（`WindowServer-2026-11-18-150030.ips`）：

```
WindowServer: WATCHDOG, monitoring timed out for service
unresponsive work processor(s): WindowServer main thread
40 seconds since last successful checkin
displayState: OFF
uptime: 760 秒
```

- 同时间段 `logd` 也卡（`com.apple.firehose.io-wl`），所以**内核日志丢失**，无法定位驱动内部
- WindowServer 线程全部 `TH_WAIT/TH_UNINT` → 阻塞在系统调用（驱动）里
- 时间点与"插拔外接屏"高度吻合

**初步判断**：外接屏热插拔触发的 framebuffer/显示管道路径在 WhateverXe 0.8.3 + 本机 eDP 补丁组合下可能死锁。

**下次复现时要收集**：

```bash
# 卡死前开一个终端跑（或另一台机器 SSH）
sudo log stream --predicate 'process == "kernel"' --level debug > /tmp/kernel.log
# 然后插拔外接屏
```

以及：

- 是否每次必现，还是偶发
- 插上时是否正常（只是拔出时卡）
- `ioreg -l | grep -i "IODisplay\|framebuffer"` 在插/拔前后的变化
- WEX 是否已更新版本修复（关注上游 issue）

**临时规避**：

- 尽量在**显示器睡眠/系统空闲**时插拔
- 或先 `pmset displaysleepnow` 再插拔
- 出现卡死时等待看门狗（约 40-60 秒）或强制重启

## 6.11 外接屏（HDMI / Type-C）没有声音（2026-11-18 查清：驱动未实现）

**现象**：接上 HDMI 或 Type-C 显示器后，系统里**没有 HDMI/DP 音频输出设备**，无声音。

### 实测数据（2026-11-18，Type-C 接 4K@60Hz 显示器）

| 检查项 | 实测 | 正常应为 |
|---|---|---|
| 显示器识别 | ✅ 3840×2160@60Hz，`Connection Type: Thunderbolt/DisplayPort` | — |
| framebuffer 端口 | `port-number = 3`，`connector-type = 0x00040000`（DP） | ✅ 正确 |
| `hda-gfx` | `onboard-1`（iGPU 与 HDA 两侧一致） | ✅ 正确 |
| `AppleHDAController` | 1 个，已加载 | ✅ |
| **`IOHDACodecDevice`** | **1**（只有模拟声卡） | **2**（模拟 + 显示音频） |
| **`AppleHDAHDMI_DPDriver`** | **0** | ≥1 |
| **`AppleHDAEngineOutputDP`** | **0** | ≥1 |
| 系统音频设备 | 只有「内建麦克风 / 内建输出」 | 应有 HDMI/DP 输出 |

### 根因：WhateverXe 没有实现显示音频

- 源码里 **没有任何显示音频实现**（`audio` 只出现在 2 处注释，无 HDA / Audio InfoFrame / ELD 相关代码）
- 因此 GPU 侧的音频 codec 从未被使能 → `IOHDACodecDevice` 一直是 1
- 这是 **驱动功能缺失**，不是配置问题；改 `hda-gfx`、connector-type、AppleALC layout 都无效

显示音频需要驱动实现：

1. 使能 GPU 的音频 codec（HDMI/DP audio enable）
2. 写 **Audio InfoFrame**（声道/采样率）
3. 通过 DPCD / AUX 读 **ELD**（显示器音频能力）
4. 与 `AppleHDAController` 完成 codec 枚举握手

### 进一步发现（2026-11-19）：组件其实都在，缺的是"使能"

| 组件 | 状态 | 说明 |
|---|---|---|
| `AppleGFXHDA.kext`（Apple 显示音频驱动） | ⚠️ **空壳** | Info.plist 有 AMD/Intel 匹配规则，但**没有二进制**（macOS 26 移除） |
| `AppleHDA.kext` / `AppleHDAController.kext` | ❌ 不存在 | macOS 26 系统里已无这些文件 |
| **`SimpleHDA`（我们 EFI 注入的第三方）** | ✅ **含完整显示音频代码** | 二进制里 `AppleHDAController` 671 处、`HDMI` 89 处、`DisplayPort` 61 处、`InfoFrame` 12 处 |
| 帧缓冲 `audio-codec-info` 属性 | ⚠️ **值为 0** | 位置：`AppleIntelFramebuffer@0`，Apple 驱动本应填入显示 codec 信息 |
| WhateverXe 源码 | ❌ 无音频实现 | 见上文分析 |

**推论**：SimpleHDA 已经具备显示音频能力，**缺的是 GPU 侧把显示 codec"叫醒"**
并把 `audio-codec-info` 填对——这正是 WhateverXe（替代了 Apple 帧缓冲）该做而没做的事。

### 下一步可行的验证（只读，低风险）

写一个小 kext，只做读取：

1. 读 HDA 控制器寄存器 `STATESTS`（偏移 0x0E）→ 看显示 codec 是否在 HDA 链路上"存在"
2. 读 GPU 侧音频寄存器（TGL `AUDIO_*`、transcoder audio enable 位）
3. dump 出来对照 Linux i915 `intel_audio.c` 的预期

- 若 codec 在链路上可见 → 只需补"使能 + 填 audio-codec-info"，**有戏**
- 若不可见 → 需要先在 GPU 侧打开音频通道（更复杂，但仍属寄存器层面）

### 探测结果（2026-11-19 02:00）

用只读探测 kext（[Tools/diagnostics/audioprobe](Tools/diagnostics/audioprobe/README.md)）读到：

```
iGPU 0x65020 = 0x80862812   ← 厂商 0x8086 + 显示音频 codec 0x2812
iGPU 0x65000 = 0x0070FA60
iGPU 0x65010 = 0x00000044
framebuffer "audio-codec-info" = 0x00000000   ← 没导出
```

**GPU 里存着显示音频 codec 的 ID，但没有导出给 macOS 音频栈。**

### 下一步（未完成）

尝试把 `audio-codec-info` 设成 `0x80862812`，看 SimpleHDA 是否识别显示 codec。
若可行，可能只需几十行代码；若不可行，仍需 WEX 实现完整音频路径（ELD + infoframe）。

### 实验记录（2026-11-19 03:00-04:00）

**实验方法**：写 kext 把 `audio-codec-info` 设为 GPU 寄存器里读到的 `0x80862812`。

**结果**：

| 阶段 | 结果 |
|---|---|
| 开机写入属性 | ✅ 成功（两个 framebuffer 都变成 `audio-codec-info = <12288680>`） |
| 插入外接屏 | ⚠️ **驱动立刻覆盖**：`av-signal-type = 0x10`（DP）、`audio-codec-info = 0x00000000` |
| 音频设备 | ❌ 仍未出现 HDMI/DP 输出（codec 数仍 1） |

**关键结论**：

1. **属性注入机制可行**（我们确实能写进 framebuffer）
2. **但驱动在每次显示变化时重新计算并覆盖** → 说明驱动内部"获取音频 codec 信息"的路径返回了空
3. `av-signal-type = 0x10` 确认是 **DisplayPort**（不是 1）
4. 因此**缺口在驱动内部**：它需要先使能 GPU 音频通道，才能取到 codec 信息

**已排除的方案**：

- ❌ 写 `audio-codec-info` 属性（被覆盖）
- ❌ 设置 `av-signal-type`（驱动自己会设对）
- ❌ 直接改 framebuffer 属性（每次热插拔重置）

**剩余可行方案**：修改 WhateverXe 的帧缓冲代码（音频使能 + ELD + infoframe），属上游工作量。

### HDMI 实测对比（2026-11-19）

在同一台机器上接 HDMI 显示器后：

| 检查项 | Type-C / DP | **HDMI** | 正常应为 |
|---|---|---|---|
| 显示器识别 | 3840×2160@60 | 3840×2160@**30** | — |
| `av-signal-type` | `0x10`（DP） | **`0x08`（HDMI）** | 正确 |
| `connector-type` | `0x00040000`（DP） | **`0x00080000`（HDMI）** | 正确 |
| `audio-codec-info` | `0x00000000` | **`0x00000000`** | 应有 codec id |
| `IOHDACodecDevice` | 1 | **1** | 2 |
| `AppleHDAHDMI_DPDriver` | 0 | **0** | ≥1 |
| 系统音频设备 | 只有内建 | **只有内建** | 应有 HDMI 输出 |

**结论：HDMI 与 DP 表现完全一致——连接器类型识别正确，但显示音频都不工作。**
这进一步确认：缺口在 WhateverXe 的音频使能，而不是某个接口的特殊问题。

（另外记录：HDMI 4K 只能到 30Hz，属 HDMI 1.4/TMDS 带宽限制，非本问题。）

### 开机时插着外接屏也不行（2026-11-19）

用 `Tools/diagnostics/audiolog` 记录开机后 3 分钟（插着 HDMI 开机）：

```
21:10:31 codec=0 hdmi=0 engDP=0 aci=（空）
21:11:23 codec=1 hdmi=0 engDP=0 aci=<00000000>   ← 只有模拟声卡
21:12:27 codec=1 hdmi=0 engDP=0 aci=<00000000>
```

| 指标 | 全程 |
|---|---|
| `IOHDACodecDevice` | 只有 `0→1`（模拟），**从未到 2** |
| `AppleHDAHDMI_DPDriver` | **恒为 0** |
| `audio-codec-info` | **恒为 0x00000000** |

**结论：开机时外接屏在场也没用**——WhateverXe 从初始化阶段就没有做显示音频使能。

### 对照：Surface Pro 4 的 Mini-DP 音频为什么能用（2026-11-19 分析）

分析了一份 Surface Pro 4 (i5-6300U, Skylake) 的 EFI（OC 0.9.6），它的 Mini-DP 音频正常工作。

**它的音频配置极其简单**：

| 设备 | 属性 |
|---|---|
| `PciRoot(0x0)/Pci(0x1F,0x3)`（HDA） | `hda-gfx = onboard-1`、`layout-id = 3` |
| `PciRoot(0x0)/Pci(0x2,0x0)`（iGPU） | `hda-gfx = onboard-1`、`framebuffer-con1-type = 0x00000800`（HDMI） |
| audio-codec-info 注入 | **完全没有** |
| 音频相关 SSDT | **一个都没有** |
| 帧缓冲驱动 | **WhateverGreen**（补丁 Apple 原生 Skylake 驱动，**不是替换**） |

**结论**：

1. hackintosh 的显示音频**不靠额外 kext 或属性注入**，而是靠 **Apple 原生帧缓冲驱动自带的音频实现**
2. `hda-gfx` 两边一致只是"配对条件"，真正干活的是 Apple 驱动
3. **WhateverXe 把 Apple 的 TGL 帧缓冲驱动整个替换了**，而 WEX 自己没写音频
   → 所以我们的 Codec 永远不被枚举、`audio-codec-info` 永远是 0

**能借鉴的**：几乎没有（配置层面我们已全部正确：`hda-gfx` 一致、connector-type 正确）。
**不能借鉴的**：WhateverGreen 方案不适用于 TGL（Apple 没有 TGL 的内置支持，这正是 WEX 存在的理由）。

**推论**：要让外接屏有声音，只有两条路
1. WEX 补上音频实现（上游工作量）
2. 让 Apple 的 TGL 驱动接管显示（WEX 存在的理由就是它不行，风险极高）

### 结论

- 本仓库层面无法修复（需要改 WhateverXe 内核驱动）
- 属于上游功能缺失，可作为 **feature request** 提交给 WhateverXe
- 临时方案：外接屏用显示器自带的 3.5mm 输出/USB 音箱，或继续用内置扬声器

**状态**：已查清，驱动限制，不修（可报上游）。

## 9. 外置 USB SSD 启动的额外注意

- 睡眠问题更明显（USB 控制器挂起/恢复）
- 强制断电后 ESP 更容易脏（见 §6）
- 建议定期备份 EFI（本仓库的 `EFI/` 即可作为备份）

## 10. 升级 macOS 前请三思

- 本配置针对 macOS 26.7.3（25G342）验证
- 大版本升级可能改变 kext 依赖（尤其 `SimpleHDA`、`WhateverXe`）
- 升级前请备份 EFI 与 AuxKC：

```bash
sudo cp -R /Library/Extensions/AppleIntelTGLCompat.kext ~/Desktop/
sudo cp /Library/KernelCollections/AuxiliaryKernelExtensions.kc ~/Desktop/
```
